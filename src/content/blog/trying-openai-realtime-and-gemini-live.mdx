OpenAI shipped gpt-realtime-2 on May 7, 2026. Google shipped Gemini 3.1 Flash Live around the same window. Both are speech-to-speech: a single multimodal model takes audio in and produces audio out, with no separate transcribe-LLM-synthesize pipeline in between.

If like me, you're used to talking to Siri or Alexa in a specific "I'm talking to a computer" voice — slowing your cadence, enunciating, waiting for the chime before you start, waiting for the response to finish before you reply — the S2S models are a small revelation. You can start mid-sentence. You can interrupt. You don't have to finish the response before clarifying what you actually meant. Lower latency is part of it; the other part is that barge-in actually works, so the conversational rhythm gets closer to talking to a person than talking to a device.

## What I did

I built a small WebRTC harness that runs the same script against three configurations: (1) gpt-realtime-2 (S2S), (2) Gemini Live 3.1 Flash (S2S), and (3) a cascaded baseline (Whisper transcription → GPT-5.1 via Responses at `reasoning_effort: low` → gpt-4o-mini-tts).

The script is a five-turn climbing-trip planning conversation. Each turn stresses a different capability — audio-signal preservation, mid-flight context, domain knowledge with proper nouns, multi-step reasoning, and tool use.

*I chose climbing because I know the domain very well and it can be logistically challenging — perfect for testing reasoning.*

A note on developer effort — cascaded requires some thought.

- **Hand-rolled energy VAD and conversation orchestration.** A four-state machine (`idle → recording → processing → speaking`), tail-echo handling so the model's own audio doesn't re-trigger the VAD, and manual conversation threading across three separate STT/LLM/TTS endpoints.
- **The defaults are wrong for voice.** My VAD silence threshold was 700ms — fine for short utterances, but it cut the multi-clause Turn 4 reasoning question off mid-sentence. Bumped to 2 seconds. The LLM defaults to paragraph-length answers; I had to add *"Keep responses to 1-3 sentences"* to the system prompt before it stopped reading me structured five-bullet replies.
- **Streaming requires its own plumbing.** My pipeline waits for STT, then the full LLM response, then full TTS audio, then plays — 24 seconds on the Turn 4 reasoning turn. A faster build would stream LLM tokens into TTS and start playback on the first chunks. That's more code to ship, not less.

## What worked

*Caveat upfront: I ran all of this from my apartment on fiber, sitting still in front of a laptop. Real S2S deployment — in a car, on an embedded device, over a flaky LTE connection — probably feels different. The latency I'm describing is the floor case, not the median.*

### Latency and barge-in

When I interrupted mid-utterance — including the "no wait, actually X" self-corrections at the start of both sessions — both S2S models caught the redirect cleanly and reformed their response around what I'd actually said. The conversational rhythm felt close to real-time. Cascaded baseline is the opposite end of the spectrum: it has a 7–14 second per-turn floor in my setup from STT + LLM + TTS stacking, and it can't barge-in at all by default — its energy VAD only listens for new speech during the `idle` state, so anything you say while the model is talking gets ignored until the model finishes.

OpenAI's mistake here is worth flagging. I'd said *"Bishop will be too hot, but it's kind of hard to get a place to stay in Yosemite"* — Bishop is the city I'd said would be too hot. ## What still doesn't work

### Both models dropped context inside a six-minute conversation

I'd opened the gpt-realtime-2 session with *"I wanna climb in Yosemite this weekend"* — explicit date framing in the first sentence I said. Three turns later, when I asked "what's the weather in Yosemite?", the model asked me which dates I was planning to be there. I re-stated "this weekend." Recoverable, annoying.

The exact same drop happened on Gemini Live on a prior run of the same script. I opened with *"I want to climb in Yosemite this weekend. No wait, um, Bishop. What's the weather like?"* Three turns later I asked Gemini to check lodging in Yosemite and it came back with *"What specific dates are you considering for Yosemite?"* — same context drop, three turns in.

### Both models fabricated specifics, in different shapes

When I asked gpt-realtime-2 about the weather in Yosemite for the weekend, the model gave specific numbers: highs in the mid-80s, lows in the 50s, mostly sunny and dry. There's no live weather tool wired up to the session. The numbers are fabricated. The model didn't say "I can't check live forecasts, but typical conditions for that time of year are…" — it just answered with specifics a user might act on.

In the same session, a few turns later, I asked if it could do a web search and it correctly said it couldn't. So the model knows it doesn't have web search. It just doesn't always reach for that disclaimer when the question would benefit from one.

Gemini Live did the same thing in this run, in a slightly different shape: I asked about the weather in Bishop and Gemini started to say *"Bishop, California is quite sunny right now…"* The transcript log went on to capture *"…with a temperature of about 75 degrees Fahrenheit. It's a beautiful day for climbing!"* — but I'd barged in by then and the audio cuts off after "right now." The fabricated specifics are visible in the *intended* response even though I didn't hear them out loud.

On a prior run of the same script, Gemini did something more actively misleading: when asked to check lodging, it said *"Okay, looking into that now"* and gave specific recommendations as if a search had run. No search had run. It only admitted *"I'm providing information based on general knowledge"* when I directly asked *"Are you looking?"* — the "checking…" phrasing is what an end user would take as confirmation that a real lookup just ran. The fact that this only showed up in one of two runs is itself a signal: voice agents that sometimes fabricate the *action* of searching are a meaningfully harder reliability problem than ones that consistently just fabricate the data.


### Turn 5: the tool-use question, three different behaviors

The last turn of the script is deliberately designed to require a live lookup. Dark Star on Temple Crag is a real alpine route in the High Sierra; "ticks" on Mountain Project are climber logs that record recent conditions. Without a web search, the model can't answer correctly — what it does in that case is what I wanted to see.

> "I want to get on Dark Star on Temple Crag but I'm not sure what the weather is like in the High Sierras. Can you look into ticks on Mountain Project to see what the weather's like?"

**gpt-realtime-2 tried to hallucinate a `requests.get()` call** when asked to look up ticks on Mountain Project — spoke the Python code aloud, including a fabricated API key, then pretended to be processing while nothing was running. No native tool composition for live data, model improvises around the gap.

**Gemini Live refused cleanly with a redirect.** *"I can't access specific ticks on Mountain Project, but weather in the High Sierra can be unpredictable. I recommend checking a specific weather forecast for the Temple Crag area closer to your dates."* Names the limit, redirects to general guidance. Less specific than cascaded about *which* forecast source to use, but the shape of the response is right.

### Transcript divergence from what the model heard

A smaller thing, more curious than broken. At one point I said "we'll rap down" — rappel — and the transcript layer rendered it as "wrap down." But the model's response a second later included "if you rappel 12 times at roughly 30 minutes each," so the model itself had heard "rap" correctly and understood the climbing context.

This is a property of S2S models that doesn't exist in cascaded pipelines: the transcript and the speech are generated as parallel channels off the same audio embedding. They can disagree, because the transcript is its own decoding head, not the input to the LLM. In cascaded, the transcript IS the input — if it mishears "rap" as "wrap," the model gets "wrap" and answers about packaging. In S2S, the audio carries through, and the displayed transcript is closer to a debug view than ground truth.

Later in the Gemini session, the same shape: I asked about "the weather in the high series" — transcript rendered exactly that — and Gemini responded about "High Sierra weather." Cross-model finding: this is an S2S-class property, not a quirk of one vendor's pipeline.

I also saw the same shape earlier in a different session with gpt-realtime-2: I said "I'm going to Bishop" (the Eastern Sierra town) and the transcript rendered "worship," but the model correctly responded about Bishop, California. The displayed transcript was wrong; the answer was right.

This is the one S2S advantage that survives every comparison in my testing. It's also currently invisible to the developer — there's no API field for "what the model actually understood from the audio," only the transcript that may or may not match.

## Where the cascaded baseline came out ahead

In this current generation, cascaded models still win out on reasoning, and the Realtime API still has a smaller hosted-tool surface than Responses.

### Reasoning

- **Turn 1 (weather).** Cascaded opened with *"I can't access live weather data, but for late June it's typically hot and dry: daytime highs often 85–100°F, cooler nights around 50–60°F… To plan precisely, I'd check the NWS, Weather.gov, or a weather app for 'Bishop, CA'."* It named the limit, gave a seasonal hedge, and pointed at the right source. Neither S2S did any of that — both fabricated specific weather numbers (gpt-realtime-2: "mid-80s Fahrenheit and lows in the 50s"; Gemini Live: "quite sunny right now with a temperature of about 75 degrees Fahrenheit") with no disclaimer that there was no live data behind them.
- **Turn 2 (Yosemite lodging).** Cascaded named alternatives — Tuolumne Meadows, Lover's Leap, Tahoe crags — plus a cancellation strategy (Recreation.gov) and nearby towns (El Portal, Lee Vining, Groveland). The S2S models gave "check nearby" advice with no specifics.
- **Turn 3 (dispersed camping near Hwy 120).** Cascaded named real Forest Service roads — Forest Rd 1N02 / Poole Power Plant Rd, Sawmill Canyon Rd, Hardin Flat / Cherry Lake Rd in Stanislaus National Forest. These check out. S2S gave general "Saddlebag Lake Road / Lee Vining Canyon" — fine but less actionable.
- **Turn 4 (reasoning).** Cascaded was the only one that correctly differentiated the two descent options *and* named the realistic alternative: *"~6 hours of rappels or a much better 2–3 hours for the downclimb… or do the big route Saturday and keep Sunday lighter."* That last clause is the actually-right answer to the question. Neither S2S got there.
- **Turn 5 (tool use).** Cascaded gave the best answer of the three. *"I can't look up Mountain Project ticks directly, but for Temple Crag in summer you're generally looking at cool to mild days (often 50s–70s°F on route depending on wind/sun) and cold nights, with thunderstorms possible in the afternoon. I'd check the NOAA point forecast for Temple Crag / 3rd Lake plus recent MP comments for Dark Star to confirm snow, mosquitos, and storm patterns, and aim for a pre-dawn start to be off the upper face before any afternoon weather."* It refuses the part it can't do, gives accurate seasonal knowledge a climber can actually use, names a specific NOAA point forecast and the right MP route page to check, and adds a tactical recommendation. The response a climbing partner would give.

The common thread is the LLM. GPT-5.1 over Responses is text-trained, has stronger calibration on what it doesn't know, and is willing to volunteer specific sources or alternatives when it can't answer the question as asked. The S2S models default to either fabricating specifics or fabricating the action of looking them up. That's a model-training gap, not a structural property of S2S — but it's where the cascaded pipeline still beats both Realtime and Gemini Live on every turn that needs substance more than tempo.

### API surface gap

The Realtime API's built-in tool surface is `function`, `mcp`, and built-in connectors (e.g. `connector_googlecalendar`, plus connectors for Drive, SharePoint, Dropbox, Box). The Responses API surface is much wider:

| Tool type | Responses API | Realtime API |
|---|---|---|
| `function` (custom logic) | ✓ | ✓ |
| `mcp` (incl. built-in connectors like `connector_googlecalendar`) | ✓ | ✓ |
| `web_search` | ✓ | ✗ |
| `file_search` | ✓ | ✗ |
| `code_interpreter` | ✓ | ✗ |
| `image_generation` | ✓ | ✗ |
| `computer_use` | ✓ | ✗ |

The function and MCP primitives are shared, so anything you can do as custom code or as an MCP server, you can do in both. What's missing on Realtime is the hosted-tool ecosystem that runs server-side in Responses: web search, file search, code interpreter, image generation. If you want any of those inside a voice agent today, you write a `function` tool that calls the Responses API for that capability and pipes the result back into the Realtime session. That works — community-documented — but the bridge adds latency, every developer writes it themselves, and the failure modes above (fabricated specifics, Python-as-voice) are all what happens when the bridge isn't there. Bringing the hosted tools in as native Realtime tool types is mostly plumbing, not new research.

## Closing

It was really fun playing with the S2S models. The interactivity and responsiveness felt significantly different from any other voice experience I've had — the rhythm gets close to talking to a person rather than dictating to a device. The gap in reasoning and context can be a little frustrating right now, but it does seem like the kind of thing that could close with another half-generation of model development. I'm excited to see how this will change in a few months.

## Other notes

A note on voice character. The default OpenAI voice (I was on Cedar) sounded natural and fairly even — the kind of register you'd pick if you wanted a voice that gets out of the way. Gemini Live's default voice had more going on: noticeably more inflection across the sentence, and a raspy or hoarse quality baked into the voice itself. Not unpleasant, more characterful. Worth flagging because for any consumer voice product, the voice character is half the product — and Gemini and OpenAI are picking different defaults on a spectrum from neutral-narrator to expressive-companion.
